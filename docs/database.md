# Database Design

## 1. Objetivo

Este documento define a estrutura de dados do **Professional Management System**.

O banco de dados principal será PostgreSQL e sua evolução será controlada por migrations utilizando Flyway.

O objetivo deste documento é garantir consistência entre domínio, banco, API e implementação.

---

# 2. Entidades principais

O sistema possuirá inicialmente as seguintes tabelas:

- users
- professionals
- contacts
- departments
- positions

---

# 3. Convenções

## 3.1 Nomes

As tabelas utilizarão nomes em inglês e `snake_case`.

Exemplos:

```text
professionals
departments
created_at
department_id
```

## 3.2 Identificadores

As tabelas utilizarão chaves primárias numéricas do tipo `BIGINT`.

A geração poderá utilizar:

```sql
GENERATED BY DEFAULT AS IDENTITY
```

ou mecanismo equivalente suportado pelo PostgreSQL e pelo Hibernate.

## 3.3 Datas

Datas e horários de auditoria utilizarão:

```text
TIMESTAMP WITH TIME ZONE
```

quando apropriado.

Campos principais:

```text
created_at
updated_at
```

## 3.4 Exclusão

No MVP, será evitado `CASCADE DELETE` entre entidades principais quando a exclusão puder remover dados importantes de forma implícita.

As regras de exclusão serão controladas pela aplicação sempre que necessário.

---

# 4. Tabela users

Representa usuários autorizados a acessar o sistema administrativo.

```sql
users
```

## Colunas

| Coluna | Tipo | Obrigatório | Regra |
|---|---|---:|---|
| id | BIGINT | Sim | Primary Key |
| name | VARCHAR(120) | Sim | Nome do usuário |
| email | VARCHAR(180) | Sim | UNIQUE |
| password | VARCHAR(255) | Sim | Hash da senha |
| role | VARCHAR(30) | Sim | Perfil do usuário |
| active | BOOLEAN | Sim | Default TRUE |
| created_at | TIMESTAMPTZ | Sim | Data de criação |
| updated_at | TIMESTAMPTZ | Sim | Data de atualização |

## Constraints

```text
PK users(id)
UNIQUE users(email)
NOT NULL name
NOT NULL email
NOT NULL password
NOT NULL role
NOT NULL active
```

O e-mail deverá ser armazenado de maneira consistente para evitar duplicidade por diferença de capitalização.

---

# 5. Tabela departments

Representa os departamentos da organização.

```sql
departments
```

## Colunas

| Coluna | Tipo | Obrigatório | Regra |
|---|---|---:|---|
| id | BIGINT | Sim | Primary Key |
| name | VARCHAR(120) | Sim | UNIQUE |
| description | VARCHAR(500) | Não | Descrição |
| created_at | TIMESTAMPTZ | Sim | Data de criação |
| updated_at | TIMESTAMPTZ | Sim | Data de atualização |

## Constraints

```text
PK departments(id)
UNIQUE departments(name)
NOT NULL name
```

## Regras

- departamentos não poderão possuir nome vazio;
- nomes duplicados não deverão ser permitidos;
- a exclusão de um departamento associado a profissionais deverá ser bloqueada.

# 7. Tabela professionals

Representa os profissionais cadastrados no sistema.

```sql
professionals
```

## Colunas

| Coluna | Tipo | Obrigatório | Regra |
|---|---|---:|---|
| id | BIGINT | Sim | Primary Key |
| name | VARCHAR(150) | Sim | Nome do profissional |
| birth_date | DATE | Não | Data de nascimento |
| status | VARCHAR(20) | Sim | ACTIVE / INACTIVE |
| department_id | BIGINT | Não | Foreign Key |
| position_id | BIGINT | Não | Foreign Key |
| created_at | TIMESTAMPTZ | Sim | Data de criação |
| updated_at | TIMESTAMPTZ | Sim | Data de atualização |

## Constraints

```text
PK professionals(id)

FK professionals.department_id
    -> departments.id

FK professionals.position_id
    -> positions.id

NOT NULL name
NOT NULL status
```

## Status

Valores inicialmente permitidos:

```text
ACTIVE
INACTIVE
```

O valor padrão será:

```text
ACTIVE
```

## Regras

- o nome deve ser obrigatório;
- a data de nascimento, quando informada, deve representar uma data passada;
- o departamento deve existir quando informado;
- o cargo deve existir quando informado;
- o status deve ser válido.

---

# 8. Tabela contacts

Representa os contatos associados aos profissionais.

```sql
contacts
```

## Colunas

| Coluna | Tipo | Obrigatório | Regra |
|---|---|---:|---|
| id | BIGINT | Sim | Primary Key |
| professional_id | BIGINT | Sim | Foreign Key |
| type | VARCHAR(30) | Sim | Tipo do contato |
| value | VARCHAR(255) | Sim | Conteúdo |
| label | VARCHAR(80) | Não | Identificação opcional |
| created_at | TIMESTAMPTZ | Sim | Data de criação |
| updated_at | TIMESTAMPTZ | Sim | Data de atualização |

## Constraints

```text
PK contacts(id)

FK contacts.professional_id
    -> professionals.id

NOT NULL professional_id
NOT NULL type
NOT NULL value
```

## Tipos

Valores inicialmente suportados:

```text
EMAIL
PHONE
MOBILE
OTHER
```

## Exemplos

```text
EMAIL
brayan@example.com

MOBILE
+55 48 99999-9999

PHONE
+55 48 3433-0000
```

## Exclusão

Quando um profissional for removido, seus contatos poderão ser removidos automaticamente.

Essa relação poderá utilizar:

```text
ON DELETE CASCADE
```

pois contatos não possuem significado independente do profissional.

# 10. Cardinalidade

## Department → Professional

```text
Department 1 : N Professional
```

Um departamento poderá possuir vários profissionais.

Um profissional poderá possuir no máximo um departamento no MVP.

---

## Position → Professional

```text
Position 1 : N Professional
```

Um cargo poderá estar associado a vários profissionais.

Um profissional poderá possuir no máximo um cargo no MVP.

---

## Professional → Contact

```text
Professional 1 : N Contact
```

Um profissional poderá possuir vários contatos.

Um contato deverá pertencer obrigatoriamente a um profissional.

---

# 11. Índices

Além dos índices criados por `PRIMARY KEY` e `UNIQUE`, serão avaliados índices para campos utilizados frequentemente em filtros.

Inicialmente:

```sql
CREATE INDEX idx_professionals_name
ON professionals(name);

CREATE INDEX idx_professionals_status
ON professionals(status);

CREATE INDEX idx_professionals_department
ON professionals(department_id);

CREATE INDEX idx_professionals_position
ON professionals(position_id);

CREATE INDEX idx_professionals_created_at
ON professionals(created_at DESC);

CREATE INDEX idx_contacts_professional
ON contacts(professional_id);
```

A criação definitiva deverá considerar as consultas realmente utilizadas pela aplicação.

Não deverão ser adicionados índices sem necessidade.

---

# 12. Busca por nome

A listagem de profissionais permitirá pesquisa parcial por nome.

Exemplo:

```text
Brayan
```

poderá corresponder a:

```text
Brayan Favarin
Brayan Silva
João Brayan
```

A estratégia inicial poderá utilizar comparação case-insensitive suportada pelo PostgreSQL.

O comportamento definitivo será implementado no Repository.

---

# 13. Integridade Referencial

O banco deverá impedir referências inválidas.

Exemplo:

```text
professional.department_id = 999
```

não deverá ser permitido caso o departamento 999 não exista.

O mesmo vale para:

```text
position_id
professional_id
```

---

# 14. Regras de Exclusão

## Professional

Ao excluir um profissional:

```text
Professional
     │
     └── Contacts
```

seus contatos associados poderão ser excluídos automaticamente.

---

## Department

Caso existam profissionais associados:

```text
Department
    │
    └── Professionals
```

a exclusão deverá ser bloqueada.

A aplicação deverá retornar um erro de negócio apropriado.

---

## Position

Caso existam profissionais associados ao cargo, a exclusão deverá ser bloqueada.

---

## User

A exclusão de usuários não será uma funcionalidade prioritária no MVP.

Poderá ser utilizada desativação:

```text
active = false
```

em vez de exclusão física.

---

# 15. Auditoria

As principais tabelas terão:

```text
created_at
updated_at
```

O preenchimento poderá ser realizado automaticamente utilizando mecanismos do Spring Data JPA.

Exemplo conceitual:

```text
@CreatedDate
@LastModifiedDate
```

ou através de callbacks JPA.

A estratégia definitiva será escolhida durante a implementação.

---

# 16. Enums

Enums Java deverão ser persistidos utilizando representação textual.

Exemplo:

```java
@Enumerated(EnumType.STRING)
```

Nunca deverá ser utilizado `ORDINAL` para enums de domínio importantes.

Exemplos:

```text
ProfessionalStatus

ACTIVE
INACTIVE
```

```text
ContactType

EMAIL
PHONE
MOBILE
OTHER
```

```text
UserRole

ADMIN
```

Isso evita problemas caso a ordem dos enums seja alterada futuramente.

---

# 17. Migrations

Flyway será responsável pela criação e evolução do schema.

Estrutura:

```text
src/main/resources/db/migration/
```

Exemplo inicial:

```text
V1__create_departments_table.sql
V2__create_positions_table.sql
V3__create_professionals_table.sql
V4__create_contacts_table.sql
V5__create_domain_indexes.sql
```

As migrations não deverão ser alteradas depois que forem utilizadas em ambientes compartilhados.

Mudanças futuras deverão utilizar novas migrations.

Exemplo:

```text
V7__add_column_example.sql
```

---

# 18. Hibernate

Durante desenvolvimento e produção, a estrutura do banco deverá ser controlada principalmente pelo Flyway.

A configuração recomendada será equivalente a:

```text
spring.jpa.hibernate.ddl-auto=validate
```

Assim, o Hibernate valida se as entidades Java correspondem à estrutura criada pelas migrations.

Não será utilizado:

```text
create
create-drop
```

em produção.

---

# 19. Dados iniciais

O banco poderá possuir dados iniciais mínimos necessários para executar o sistema.

O principal caso será a criação de um usuário administrador inicial.

Por questões de segurança, credenciais reais de produção não deverão ser armazenadas diretamente nas migrations.

A estratégia poderá utilizar:

- variáveis de ambiente;
- inicialização segura da aplicação;
- script específico de ambiente.

A decisão definitiva será realizada durante a implementação da autenticação.

---

# 20. Banco de Testes

Testes de integração não deverão utilizar o banco de produção ou desenvolvimento.

Será utilizado um ambiente isolado.

A estratégia preferencial será:

```text
Testcontainers
+
PostgreSQL
```

Isso permite testar a aplicação utilizando o mesmo mecanismo de banco empregado em produção.

---

# 21. Configuração

Credenciais não deverão ser armazenadas no Git.

Exemplo:

```text
DB_HOST
DB_PORT
DB_NAME
DB_USERNAME
DB_PASSWORD
```

A aplicação deverá consumir essas configurações através de variáveis de ambiente.

---

# 22. Decisões do MVP

| Tema | Decisão |
|---|---|
| Banco | PostgreSQL |
| Migrations | Flyway |
| IDs | BIGINT |
| Naming | snake_case |
| Professional → Contact | 1:N |
| Department → Professional | 1:N |
| Position → Professional | 1:N |
| Usuário | Conta administrativa |
| Exclusão de contatos | Cascade com Professional |
| Exclusão de Department | Bloqueada quando utilizado |
| Exclusão de Position | Bloqueada quando utilizado |
| Enum | Persistido como String |
| Hibernate schema management | Validate |
| Auditoria | created_at + updated_at |

---

# 23. Questões para evolução futura

Algumas alterações poderão ser avaliadas após o MVP:

- soft delete de profissionais;
- histórico de alterações;
- auditoria de usuário;
- múltiplos cargos por profissional;
- histórico de cargos;
- múltiplos departamentos;
- endereços;
- documentos;
- foto de perfil;
- multiempresa;
- UUID como identificador externo.

Esses recursos não fazem parte da primeira versão.

---

# 24. Resultado Esperado

O modelo definido neste documento deverá fornecer uma base consistente para a implementação da API e evitar que regras importantes de integridade dependam exclusivamente do código da aplicação.

Mudanças significativas no modelo deverão ser refletidas neste documento e implementadas através de novas migrations.
